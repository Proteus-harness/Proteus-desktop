# Работа С Proteus-desktop

Основной клиент Proteus на GPUI. src/ — приложение, crates/client-common —
общие правила подключения и синхронизации, crates/diff — разбор diff,
crates/tabs — модель вкладок и областей без GPUI, examples/ — примеры расширений
и каталогов. Пользовательская документация — README.md, на русском языке.
Rust toolchain задан rust-toolchain.toml.

## Границы

Клиент использует публичный HTTP/SSE app-server и DTO proteus-contracts из
закреплённой Git-ревизии Proteus-core. Не импортируйте Core или реализации
модулей в UI. Поставляемые расширения живут в Proteus-desktop-extensions и
используют тот же публичный процессный протокол, что и пользовательские.
В клиенте остаются общий рендерер и нативные примитивы; логику конкретного
расширения пишите в его пакете. Не возвращайте builtin registrations или
специальные ветки по id расширения.

Держите файлы небольшими и связными, при 500–700 строках ищите разумное
разделение. Сохраняйте текущий native workflow, клавиатуру, фокус и состояние
сессии. Черновой протокол меняется вместе со всеми producers/consumers, без
legacy aliases или dual-read. Текущий сценарий — доверенные собственные
процессы; sandbox/hardening не добавляйте без поручения владельца.

## Стоимость Обновлений

Для новых и изменяемых затратных путей применяйте общий стандарт
[расхода ОЗУ](https://github.com/Proteus-harness/Proteus-core/blob/main/docs/development/memory.md):
ownership/lifetime, совокупные бюджеты, ленивую подготовку, очереди и замеры.
При соседних checkout документ находится в `../Proteus-core/docs/development/memory.md`.

- Для свёрнутой строки считайте только видимые summary/stats; подробный diff,
  labels и форматирование готовьте там, где они нужны. Общий разбор должен
  сохранять те же границы файлов, counts и обработку некорректного ввода.
- Не копируйте неизменённый source ради сравнения. Проверяйте также context
  и contributors: одинаковый текст не означает неизменившийся renderer.
  Между retained UI и runtime разделяйте immutable snapshot; полный owned
  payload для wire создавайте после допуска очередью, не для вытесненных edits.
- Coalescing разрешён только для заменяемого latest content. Сохраняйте
  in-flight revision, ACK и content_error, action sequence, session/rehost,
  restart и invalidation без смены source. Отмена или устаревший ответ сами
  по себе не освобождают чужой in-flight запрос; journal/terminal events
  нельзя терять как промежуточные перерисовки.

Проверяйте эти границы существующими focused тестами. Удаление повторной
allocation видно в исходниках; улучшение latency/RSS/CPU — только в замере
с одинаковыми revisions, входами и cold/warm режимом. Не обещайте ускорение
всего приложения по одной устранённой копии.

## Источники И Проверка

repositories.json закрепляет Core, модули и стандартные расширения для
поставки. scripts/sources.py использует явный PROTEUS_*_SOURCE, соседние
checkout ../Proteus-core, ../Proteus-modules, ../Proteus-desktop-extensions или
загружает закреплённые revisions в build/sources.
Cargo dependencies также закреплены commit, без обязательных соседних путей.

Для локальной правки выберите затронутый target по
[руководству по сборке и проверкам](BUILDING.md#запуск-и-проверки).
Для изменения UI проверьте взаимодействие в нативном окне.
Берите готовые синтетические чаты или seeder по
[правилам работы с корпусами](BUILDING.md#корпуса-и-измерения).
При изменении общего протокола проверьте клиент вместе с расширениями.

После проверенной правки приложения создайте отдельный commit и обновите
Desktop в рабочей поставке. При совместном изменении выберите затронутые
компоненты по [таблице сборки](BUILDING.md#выбор-компонентов).
Сохраняйте инкрементальный кэш. В замерах укажите собранные компоненты,
состояние кэша и фактические показатели.

GitHub Actions запускаются вручную и по релизным тегам `v*`; обычные push и PR
не запускают проверки. Сохраняйте этот режим без отдельного запроса владельца.
Секреты и реальные сессии не публикуйте.

Тесты должны защищать поведение или контракт. Не копируйте целую палитру
из JSON в Rust fixtures и не фиксируйте отдельными тестами текущие проценты
декоративного смешения: проверяйте реальные поля схемы, читаемость и состояния.
При падении UI-теста проверьте, что его окно получило те же настройки, что и
обычное окно приложения. [Разбор падений в Core](https://github.com/Proteus-harness/Proteus-core/blob/main/docs/development/testing.md#разбор-падений).
В native-крейте integration target заставляет Cargo также собрать обычный
GUI-бинарник. Если он не нужен проверяемому сценарию, проверки встроенных
шейдеров и других данных держите в unit-модуле. Для небольшой правки выбирайте её
focused-проверки, полный применимый набор выполняйте перед публикацией.

## Zed Как Образец

Для редактора, панелей, дерева файлов, git, вкладок, меню, клавиатуры, фокуса
и анимаций найдите соответствующую реализацию в исходниках Zed (`~/Code/zed`
или [репозиторий Zed](https://github.com/zed-industries/zed)). Воспроизведите
поведение, раскладку, тексты и клавиши средствами наших примитивов.
При переносе кода укажите источник в начале файла, например
`// Адаптировано из Zed: crates/<путь>`.
Отступление от Zed — только по просьбе владельца или когда нужного примитива
нет; тогда опишите разницу в отчёте.

## Единый Стиль

Правила вида и поведения — в [DESIGN.md](DESIGN.md): текст, раскрытие, меню, вкладки,
кнопки и состояния. Перед работой над интерфейсом прочитайте его; заметил
владелец новый нюанс — допишите правило туда же сразу, вместе с исправлением.
Прежде чем писать элемент, найдите его аналог в Zed и уже готовый аналог у
нас; два разных решения одной задачи сведите в одно общее и переведите на него
остальные места. Новый примитив делайте общим, опишите в его модуле, для чего
он, и перечислите в отчёте переведённые места.

Лицензии как в Zed: в корне LICENSE-GPL и LICENSE-APACHE, у каждого крейта
поле `license` в Cargo.toml и symlink на тот же файл корня. Приложение —
GPL-3.0-or-later; crates/client-common — Apache-2.0. В Apache-крейт можно
переносить только код Apache-крейтов Zed (gpui*, collections, sum_tree, util
и т. п.), код GPL-крейтов (ui, git_ui, project_panel, editor…) — нельзя.
Проверка: `python3 scripts/check_licenses.py [КОРЕНЬ]`, её запускает
scripts/test.py для клиента и расширений.
