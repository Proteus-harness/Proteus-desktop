# Время и стоимость модульной сборки

Постоянный Linux-стенд запускает обычный `scripts/portable.py --no-archive`:
по умолчанию только Desktop, с готовыми Core/модулями/расширениями из
`build/Proteus`. `--components desktop extensions` измеряет эти два компонента;
`--full` явно выбирает все четыре. Измерение не расширяет scope автоматически. `fast` и повторное
использование готовых бинарников не включаются. `target` и кэш ОС сохраняются.
Первый запуск измеряет сборку текущих изменений с имеющимися зависимостями,
следующие — повторную сборку без намеренного изменения исходников. Это **не**
холодная сборка с пустым Cargo-кешем.

```sh
python3 examples/performance/build-cost/run.py \
  --output "$PWD/build/performance/build-20261029" --jobs 2 --runs 2
```

Стенд сохраняет исходные revisions/dirty paths, полный build log, GNU time
(wall/user/system, page faults, максимальный RSS отдельного процесса), выборки
уже общего Core `proc_sampler` и одновременные пики PSS/RSS дерева сборки.
PSS — основной показатель физической памяти; max-process-RSS не складывается
с пиками дерева. Короткие процессы между выборками могут быть пропущены.
Итог также содержит реально напечатанные команды/скомпилированные packages,
число узлов и рёбер Cargo resolve только выбранных компонентов для Linux (включая dev/build dependencies),
число workspace packages и размеры готовой portable-папки/бинарников.

Результат пишется в новый output, существующие замеры не перезаписываются.
Во время сборки не запускайте runtime-бенчмарки; их CPU/время будут искажены.
Раннер использует тот же выбор локальных/закреплённых sources только выбранных компонентов, что portable;
`--core-source` задаёт только место общего sampler.
